# Rebound MVP: feature research and implementation boundaries

Source access was checked during this MVP update. This is a focused review of official patient guidance, browser documentation, and accessibility guidance. It is not a systematic clinical review, evidence that Rebound improves recovery, or validation of the app's pose estimates.

Avoid guilt-based streaks, invented recovery percentages, automatic return-to-sport clearance, and comparative leaderboards. The research read here does not establish that these improve clinical recovery. The MVP should help someone understand and follow an appropriate plan, rather than reward exercising through symptoms.

## Reminder delivery: what the platform actually supports

### In-app and open-page reminders

A loaded application can evaluate local routine days/time, create an inbox item, and try to show a system notification after permission has been granted. It should re-evaluate when the page becomes visible again. Browsers throttle inactive-page timers, so callbacks are not an exact clock.

Use a bounded same-day catch-up window, stable routine/date identifiers, persistent deduplication, and snooze/dismiss controls. A prior dismiss or a completed plan should not generate repeated alerts. Scheduling time and intended exercise frequency must come from the user or clinician, not from a notification algorithm.

An API call resolving does not prove that a person saw a notification. Focus modes, OS settings, browser policy, and device state may suppress presentation. Prefer labels such as “Sent to browser” or “Test requested” over “Delivered.” An inbox entry means the app recorded a reminder, not that the operating system displayed it.

### Mobile and closed-app delivery

The canonical MDN Notifications API source states that the `Notification()` constructor throws a `TypeError` on most mobile browsers. Mobile notification support therefore must not be inferred from desktop constructor support. Prefer persistent notifications through `ServiceWorkerRegistration.showNotification()` when a usable registration exists, and handle unsupported states honestly.

MDN browser-compatibility data currently records Safari on iOS notification support from 16.4 with important conditions: the site must be a web app saved to the home screen, its manifest must have a non-default `display` value, and notifications can only be sent from a service worker. The PushManager compatibility data also identifies home-screen installation. These findings came from Mozilla's canonical compatibility data; the official WebKit announcement itself was blocked by this environment and was not read.

A service worker is event-driven. Registering one, showing a persistent notification, or placing `setTimeout()` inside it does **not** create a dependable future scheduler. Server-sent Web Push can start a service worker as needed; that is a separate architecture from local reminders. The present MVP should explicitly say that it has no server-scheduled background push. An imported calendar is a practical alternative, with alarm behavior controlled by the calendar platform.

### Consent and privacy

Permission requests belong to an intentional action such as “Enable browser alerts,” not page load. Denial is a supported state; do not continually prompt. Provide a useful non-notification path and a way to turn reminders off.

Default lock-screen content should be generic, such as “Your personal recovery check-in is ready,” without an injury name, discomfort score, clinician note, or other health detail. Detailed information stays inside the application. This is a privacy design recommendation; it does not by itself make the application compliant with a medical-data regulation.

## Minimum release evidence

Before calling this a tested MVP, verify the built application, not only isolated helper functions:

1. A new user can create a routine, choose their own days/time, and see an accurate daily plan without fabricated progress or a medical score.
2. Reminder settings persist; due items deduplicate across reloads; snooze/dismiss work; no permission prompt appears on load; denied/unsupported states remain usable.
3. Calendar output parses and retains the selected routine days, local time, escaped text, stable identity, and intended reminder. Test import in representative calendars before claiming alarm compatibility.
4. Browser alerts are tested separately from in-app inbox creation. Test foreground, background, resumed page, denied permission, iPhone home-screen mode, Android, and desktop. Document delayed or suppressed behavior. Do not claim closed-app push without a deployed scheduler and subscription flow.
5. Plan completion reflects the actual routine sequence, not any unrelated exercise session. Safety holds still block generic exercise. A self-reported symptom change never automatically authorizes more exercise.
6. Empty states, readable controls, keyboard navigation, focus management, reduced motion, and mobile layout are checked. Use comfortable touch sizes rather than targeting the WCAG minimum everywhere.
7. Exported summaries show only recorded observations with a date range and clear missing-data labels; exports are deliberate and local. Avoid exposing health details in alerts.
8. The existing medical catalog, source limitations, and pose-recognition limitations remain visible. Clinical suitability, real-person camera accuracy, and privacy/release review remain separate work.

“Paid-quality” is a product goal, not a measured research outcome. For this app it should mean dependable state, clear source boundaries, respectful reminders, readable design, and complete core flows before adding more screens.

## Delivered in this update

The implementation includes the daily plan and actual routine completion/resume, opt-in local reminders with private text, browser-alert support, snooze/dismiss/deduplication, recurring calendar export, saved clinician questions and a locally printable visit summary, clearer navigation, and reduced-motion/static guides. The journal remains a daily check-in; a separate before/after-per-session symptom workflow is a candidate for later review, not a shipped treatment feature. Server-scheduled background push, clinical outcome validation, real-person camera accuracy, physical-phone notification testing, and representative calendar-import testing remain release work.

The final automated suite has 40 passing checks. Browser-alert tests use a mocked permission/notification worker API to verify the application's behavior; they do not prove OS presentation, background wake-up, or iPhone delivery. The existing camera test loads the real on-device model with synthetic video, not a clinical or real-person accuracy study.
